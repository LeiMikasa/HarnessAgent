# minicode 本轮改动总结

整理日期：2026-10-22

这几轮修改主要解决两件事：**让 Agent 更准确地找到项目代码，让它修改文件时更谨慎。**

如果你想结合代码理解，建议先读后面的[代码跟读：从一次请求走到文件修改](#代码跟读从一次请求走到文件修改)。前面的章节用来查阅改动概览。

## 一、已有文件必须先读，才能修改

以前主要通过提示词要求 Agent“先读再改”，模型直接调用修改工具时，程序仍可能执行。

现在，`write_file` 和 `edit_file` 会执行真正的检查：如果当前会话没有读过某个已有文件，就拒绝修改，并要求先使用 `read_file`。

例如：

```text
Agent：把 config.py 改成这些内容。
工具：你还没读过这个文件，先读取，再修改。
```

完全权限模式和单次宿主机批准也不会跳过这项检查。

## 二、读取后文件变了，需要重新读取

读取文件时，程序会记录文件身份、修改时间、大小、权限位和内容摘要。可以把这些信息理解成文件的“指纹”，不是 Git 提交号。

```text
Agent 读到：port = 8080
你手动改成：port = 9090
Agent 准备按旧内容修改
工具发现文件版本变化，拒绝修改，要求重新读取
```

这能拦住“拿着旧内容修改新文件”的常见情况。程序不会自动合并双方的修改；模型需要读取最新内容，再决定如何调整。

## 三、新建文件和连续修改仍然方便

| 情况 | 工具的处理 |
|---|---|
| 创建不存在的新文件 | 允许直接创建 |
| 刚创建成功，接着编辑 | 允许 |
| 刚修改成功，再继续修改 | 允许 |
| 修改已有但没读过的文件 | 拒绝，要求先读 |
| 读完后文件被其他人修改 | 发现版本变化后拒绝，要求重读 |
| 创建文件时，其他人抢先创建了同名文件 | 拒绝覆盖，保留对方文件 |

成功创建、覆盖或编辑后，程序会更新观察记录，因此不需要每次修改前都机械地重复读取。

## 四、先写临时文件，再替换目标

文件写入改成了以下流程：

```text
准备新内容
→ 写入本次操作专用的临时文件
→ 写完并刷新到磁盘
→ 再检查目标文件有没有变化
→ 发布新文件或替换原文件
→ 更新观察记录
```

如果准备临时文件时写入失败，原文件可以保留下来。

同时处理了这些细节：

- 编辑文本时保留原来主要使用的 CRLF 换行方式。
- 覆盖时保留原文件的权限，Windows 替换还会保留目标访问控制信息。
- 失败后尝试清理本次生成的临时文件，包括 Windows 只读临时文件。
- 无法确认发布结果时，将执行状态标记为“未知”，要求读取实际文件后再恢复。
- 新建使用不可覆盖的发布方式，避免覆盖同时出现的同名文件。

## 五、不同 Agent 分别记录自己读过什么

主 Agent、子 Agent 和队友各自保存读取记录。

```text
主 Agent 读过 config.py
不代表子 Agent 也读过 config.py
```

| 情况 | 读取记录如何处理 |
|---|---|
| 主 Agent 在同一 Runtime 中继续对话 | 保留 |
| 队友继续自己的多轮工作 | 保留自己的记录 |
| 创建子 Agent | 使用独立记录 |
| CLI/TUI 使用 :clear 清空对话 | 清除主 Agent 的记录 |
| 重启服务、恢复或重建 Runtime | 需要重新读取已有文件 |

读取记录只存在内存里，不随聊天存档持久化。**聊天还在，不代表服务重启后可以直接覆盖文件。**

普通分段读取也会建立版本观察：这项检查判断文件有没有变化，不判断模型是否完整读懂了文件。已有的“未知写入状态”保护仍然要求完整、未截断的读取，或者确认文件不存在，才能解除。

## 六、搜索默认跳过依赖和构建目录

`glob` 和 `grep` 默认跳过以下目录：

```text
node_modules  .venv  venv  .git  __pycache__
dist  build  coverage  .next  .nuxt  .cache
```

这是在进入目录前跳过，减少遍历工作，也避免大量依赖结果淹没项目源码。

确实需要检查这些目录时，可以明确指定目录，或者设置 `include_ignored=true`。后者也会包含隐藏路径，但不会扩大原有文件访问权限。

例如：

```text
glob({"pattern": "web/**/*.ts"})
默认跳过依赖目录。

glob({"pattern": "web/node_modules/**/*.ts"})
明确指定后，可以搜索依赖目录。
```

这里使用固定的排除名单，没有实现完整的 `.gitignore` 解析。

## 七、参数写错时，返回明确错误

例如，工具不支持这种花括号展开：

```text
*.{ts,vue}
```

以前可能返回“没有匹配”，让模型误以为文件不存在。现在会返回参数错误，说明应分别搜索不同的模式。

检查适用于 `glob.pattern` 和 `grep.include`，不影响 `grep.pattern` 中合法的正则表达式量词，例如 `x{2,3}`。

## 八、项目分析要求找到核心实现再下结论

提示词补充了以下阅读顺序：

```text
明确当前需要回答的问题
→ 从 README 和相关目录找到入口
→ 搜索核心函数定义
→ 阅读具体实现和必要的调用方
→ 证据足够后回答
```

同时要求区分：文档怎么描述、代码实际怎么实现、哪些行为经过运行验证。

仓库里的提示词、注释和 Git 记录，不能用来断言当前 Agent 的运行身份，也不能仅凭这些材料断言项目在“用自己开发自己”。

**目录排除和参数校验由程序执行；阅读方法、结论是否谨慎，仍需要模型遵守提示词。**

## 九、Docker 错误反馈更加明确

| 情况 | 含义和下一步 |
|---|---|
| 沙箱启动失败 | 请求的命令还没运行，需要先恢复沙箱环境 |
| 命令提交后返回失败 | 检查退出码、输出和实际结果 |
| 执行超时 | 可能已经产生修改，先检查实际状态 |

遇到沙箱启动失败后，同一轮任务的后续模型请求会继续收到提醒：换一条命令不能修复 Docker。

这项提醒不强制禁用 Bash，也不会自动绕过权限转到宿主机执行。

本次机器上的具体故障是缺少 `minicode-sandbox:dev` 镜像。镜像已经构建完成，真实容器启动、Bash 执行和文件共享验证通过。

## 十、错误码速查

| 错误码 | 可以怎样理解 |
|---|---|
| `FS_NOT_OBSERVED` | 当前会话还没读过这个已有文件，先读再改 |
| `FS_STALE_VERSION` | 文件版本变了，重新读取后再决定如何修改 |
| `FS_NOT_FOUND` | 编辑目标被确认不存在，需要检查路径或使用创建操作 |
| `FS_IO_ERROR` | 文件写入或发布出错，按结果中的执行状态检查实际文件 |
| `STATE_CHECK_REQUIRED` | 上次写入结果不确定，需要完整读取或确认不存在 |
| `INVALID_ARGUMENT` | 工具参数写错，需要纠正 |
| `SANDBOX_UNAVAILABLE` | 沙箱无法启动请求的命令，需要恢复环境 |

## 十三、保护范围和边界

这套保护接在已注册的 `read_file`、`write_file`、`edit_file` 上。Shell、MCP 和其他程序的直接文件操作仍然按各自权限执行，不经过这套观察检查；之后使用文件工具修改时，会核对实际版本。

同一进程内，通过这些文件工具进行的修改会按目标文件串行执行。外部进程不持有这个锁：准备阶段的改动可以被再次检查发现，但最后检查与替换之间仍有短暂竞争窗口，因此不能保证消除所有外部并发写入问题。

进一步的实现说明见：[文件工具写前读取与版本保护](文件工具写前读取与版本保护.md)。

## 代码跟读：从一次请求走到文件修改

下面始终使用同一个例子：**把 `config.py` 中的 `port = 8080` 改成 `port = 9090`。**

代码摘自当前实现；有些片段只摘关键行，有些补了中文注释。文件名都可以点击打开。

### 第一步：模型只是提出工具请求，Python 程序负责执行

模型可能返回这样的请求：

```json
{
  "name": "edit_file",
  "input": {
    "path": "config.py",
    "old_text": "port = 8080",
    "new_text": "port = 9090"
  }
}
```

这里的 `name` 表示使用哪个工具，`input` 表示传给工具的参数。模型输出这些文字，并不会直接修改磁盘。

实际调用路线是：

```text
模型返回工具请求
→ loop.py 的 execute_tool()：校验参数、执行权限检查
→ registry.py 的 dispatch()：找到对应工具函数
→ basic.py 的 run_edit_file()：检查文件访问边界
→ filesystem.py 的 ObservedFiles.edit()：检查读取记录和版本
→ 条件满足后，才发布文件修改
→ 把成功或失败结果返回给模型
```

这次新增的文件保护位于上述后半段，原来的参数校验和权限检查仍然保留。

### 第二步：先认清 ctx、files 和 _observed

[registry.py](../agent/tools/registry.py) 的 `ToolContext` 中新增了这一行：

```python
files: ObservedFiles = field(default_factory=ObservedFiles, repr=False, compare=False)
```

可以把它读成：**每个工具上下文默认都带一本自己的“文件读取记录本”。**

| 代码名字 | 在例子中的含义 |
|---|---|
| `ctx` | 当前执行工具的环境，包括谁在执行、工作目录和权限相关信息 |
| `ctx.files` | 当前调用者使用的文件保护对象 |
| `ctx.files._observed` | 记录本，保存文件路径对应的已知版本 |
| `default_factory=ObservedFiles` | 创建上下文时默认新建一本记录本，避免大家共用同一个对象 |

`repr=False`、`compare=False` 只是避免把这个内部对象放进默认打印和比较逻辑，不决定保护规则。

在 [filesystem.py](../agent/tools/filesystem.py) 中，记录本实际上是一个字典：

```python
self._observed: dict[str, FileVersion | None] = {}
```

它不保存文件正文，只保存版本信息。查不到某个路径时，用一个专用标记表示“没看过”：

```python
_UNSEEN = object()

return self._observed.get(_key(path), _UNSEEN)
```

必须区分以下三种状态：

| 查到的值 | 含义 | 举例 |
|---|---|---|
| `_UNSEEN` | 从没观察过 | Agent 没有读取过 `config.py` |
| `None` | 已经检查过，确认不存在 | Agent 读取 `new.py`，工具确认没有这个文件 |
| 一个 `FileVersion` 对象 | 看过文件，记住了那个版本 | Agent 读过 `config.py`，记住版本 A |

“没看过”和“确认没有”是两件事，所以不能都用 `None` 表示。

### 第三步：read_file 在返回正文时，也记下版本

[basic.py](../agent/tools/basic.py) 的读取入口现在会调用：

```python
text = ctx.files.read(path)
```

对应的 `ObservedFiles.read()` 是：

```python
def read(self, path: Path) -> str:
    with _locked(path):
        snapshot = _snapshot(path)
        if snapshot is None:
            self._record(path, None)
            raise FileNotFoundError(f'no such file: {path}')
        text = _normalize(snapshot.data.decode("utf-8", errors="replace"))
        self._record(path, snapshot.version)
        return text
```

按顺序解释：

1. `_locked(path)`：取得这个目标文件的锁，协调本进程内使用同一套工具的操作。
2. `_snapshot(path)`：读取当前文件内容和版本信息。
3. `snapshot is None`：文件不存在；先记录“确认不存在”，再把不存在的结果返回上层。
4. `decode()` 和 `_normalize()`：把字节转成文字，并统一内部使用的换行形式。
5. `_record(path, snapshot.version)`：记住本次实际看到的版本。
6. `return text`：把正文交回上层工具，再按 offset/limit 截取给模型看。

假设第一次读到 `port = 8080`，这时记录本中相当于写入：

```text
config.py → 版本 A
```

### 第四步：文件版本由什么组成

`_snapshot()` 中有两行关键代码：

```python
version = FileVersion(_metadata(current), hashlib.sha256(data).digest())
return Snapshot(data, version, stat.S_IMODE(current.st_mode))
```

这里分开保存了三件东西：

| 内容 | 用途 |
|---|---|
| `data` | 本次读到的文件字节，用于返回文字或计算替换 |
| `version` | 文件身份、大小、修改时间、权限位等信息，以及内容摘要 |
| `mode` | 文件原有权限位，发布新内容时尽量保留 |

`sha256(data)` 可以理解为根据整份内容计算的指纹。即使别人把文件改成同样的大小，又恢复了原修改时间，内容指纹仍能帮助发现变化。

`_snapshot()` 还会核对读取前后以及路径和文件句柄的信息，避免一边读取、一边发生变化时，把不稳定的内容当成可靠版本。

### 第五步：修改时，把“上次看到的”和“现在实际的”进行比较

先看 `write()`，它完整的主要流程很短：

```python
def write(self, path: Path, content: str) -> None:
    with _locked(path):
        expected = self._get(path)
        current = _snapshot(path)
        self._check(path, current, expected)
        self._publish(path, content.encode("utf-8"), current, expected)
```

这里只要记住两个变量：

```text
expected：这名 Agent 上次看到的版本
current：磁盘上现在实际的文件快照
```

`_check()` 决定能不能继续，`_publish()` 才真正写入和发布。因此检查抛出错误后，下面的发布步骤不会执行。

#### 场景 A：没读过，就想覆盖已有文件

`_check()` 中的实际分支是：

```python
if expected is _UNSEEN:
    if current is not None:
        raise ToolError("FS_NOT_OBSERVED", ...)
```

上面省略了完整错误文字。条件的含义是：

```text
expected 是“没看过”
并且 current 表明文件确实存在
→ 拒绝覆盖
```

如果文件不存在，`write()` 可以继续创建。但 `edit()` 另外传入 `editing=True`，它在没有观察记录时会更早拒绝，因为编辑必须有已知目标。

#### 场景 B：读过，但文件被你改了

后面的实际版本比较是：

```python
elif (current.version if current else None) != expected:
    raise _stale(path)
```

可以把它展开理解成：

```text
记录本：config.py 是版本 A，内容为 port = 8080
磁盘上：config.py 已是版本 B，内容为 port = 7070

版本 B != 版本 A
→ 返回 FS_STALE_VERSION
→ 不执行这次文件修改
```

工具会要求模型重新调用 `read_file`。重新读完后，记录本变成版本 B，模型才能基于新内容决定改法。

### 第六步：edit_file 先过版本检查，再做文本替换

在 `ObservedFiles.edit()` 中，关键顺序是：

```python
expected = self._get(path)
current = _snapshot(path)
self._check(path, current, expected, editing=True)
content = _normalize(current.data.decode("utf-8"))
old_text, new_text = _normalize(old_text), _normalize(new_text)
count = content.count(old_text)
```

也就是先判断文件能不能改，再去找 `old_text`。

这对报错很重要：如果你已经把 `port = 8080` 改掉了，工具会优先说“文件版本变了”，而不是让模型误以为只是它提供的替换文字不准确。

通过版本检查后，仍然保留原有文本替换规则：找不到旧文字就拒绝；找到多处时，默认也拒绝，除非明确指定 `replace_all=True`。

### 第七步：通过检查之后，如何真正写入

`_publish()` 不会立刻向原文件写入，而是先写本次调用专用的临时文件：

```python
with os.fdopen(fd, "wb") as stream:
    stream.write(data)
    stream.flush()
    os.fsync(stream.fileno())
```

三行分别表示写入字节、刷新 Python 缓冲、请求操作系统同步文件数据。临时文件名随机生成，并使用排他创建，避免误用别人的临时文件。

为什么写完后还要检查一次：

```python
self._check(path, _snapshot(path), expected)
```

因为准备临时文件也需要时间。你可能正好在这段时间里修改了原文件，所以发布前会再次核对。

通过后，才进入以下分支：

```python
if current is None:
    os.link(temporary, path)
else:
    _replace_existing(temporary, path)
```

这是省略了异常处理的关键分支。

| 分支 | 实际目的 |
|---|---|
| 文件原本不存在 | 用 `os.link()` 发布新文件；目标已经存在时会失败，不会覆盖抢先创建者 |
| 文件原本存在 | 用完整的临时文件替换目标；Windows 使用 `ReplaceFileW` 保留目标访问控制信息 |

发布后，程序还会检查实际内容是否符合这次写入，并调用：

```python
self._record(path, committed.version)
```

所以一次成功修改后，记录本会从版本 A 更新成版本 B，允许这名 Agent 继续编辑。

### 第八步：错误怎样回到模型，让它重新读取

在 [basic.py](../agent/tools/basic.py) 中，文件工具会把保护异常转换成结果：

```python
try:
    ctx.files.write(path, content)
except (OSError, ToolError) as exc:
    return ToolResult.from_exception(exc)
```

随后 [loop.py](../agent/loop.py) 使用 `output.model_content()` 生成模型看到的内容，并把 `is_error` 设为失败。

例如，没读过就覆盖时，模型会收到包含这些字段的结果：

```json
{
  "ok": false,
  "error_code": "FS_NOT_OBSERVED",
  "next_action": "reread",
  "execution_status": "not_executed"
}
```

模型能据此知道：这次没改成功，下一步需要读取。工具负责拒绝不满足条件的操作；重新读完后如何修改，仍由模型决定。

### 第九步：主 Agent、子 Agent、队友为何不会混用记录

`ToolContext.child()` 创建子上下文时，默认没有把父上下文的 `files` 传进去，所以子上下文会通过 `default_factory` 得到新对象。

队友则需要跨自己的多轮调用保留记录，因此 [teams.py](../agent/teams.py) 在构造队友时创建：

```python
self.file_observations = ObservedFiles()
```

之后每次构造队友自己的工具上下文，都显式传入：

```python
files=self.file_observations
```

可以理解成：**每名队友有自己的记录本，每次上工都带同一本。**

CLI/TUI 清空对话时会执行 `runtime.lead_ctx.files.clear()`，避免历史已经清掉了，却还保留主 Agent 过去读过哪些文件的记录。

### 第十步：搜索改动对应哪几行代码

搜索的入口现在调用 [search.py](../agent/tools/search.py) 中的 `glob_paths()`。它在扫描目录时有这个判断：

```python
if not include_ignored and os.path.normcase(entry.name) in ignored and (
        entry.is_dir() or entry.name == ".git"):
    continue
```

这里的 `continue` 就是实际跳过操作：遇到 `node_modules` 等目录，不再进入里面递归。

`include_ignored=True` 会让这个默认排除判断失效；模式里明确写出的目录名也会从排除名单中移除。因此可以默认搜源码，也能有意去检查依赖。

不支持的花括号写法，则在 [basic.py](../agent/tools/basic.py) 的搜索入口被拦住：

```python
if has_brace_expansion(pattern):
    return tool_error("INVALID_ARGUMENT", ...)
```

这表示“参数不支持”，与“合法搜索但没有结果”分开。

### 第十一步：Docker 故障提醒是怎样保留下来的

[sandbox.py](../agent/sandbox.py) 将已识别的启动失败转换成 `SandboxUnavailable`，带上 `SANDBOX_UNAVAILABLE` 错误码。

[feedback.py](../agent/tools/feedback.py) 看到错误后，记录一个标记：

```python
if result.error_code == "SANDBOX_UNAVAILABLE":
    self._sandbox_unavailable = True
```

后续 `render()` 根据标记生成提醒。循环中已有的代码会把提醒加进下一次模型请求：

```python
execution_note = execution_feedback.render(ctx)
if execution_note:
    system_prompt += "\n\n" + execution_note
```

所以模型不仅能在历史工具结果里看到 Docker 失败，下一次调用时还会被明确提醒“先恢复环境，换命令不能解决这个问题”。这段代码追加提醒，没有直接禁止后续 Bash 调用。

### 最后，沿着例子完整走一遍

| 顺序 | 执行动作 | 记录本和文件的变化 |
|---|---|---|
| 1 | 直接 edit_file 改 `config.py` | 没读过，拒绝；磁盘不变 |
| 2 | read_file 读到 `port = 8080` | 记录版本 A |
| 3 | 你改成 `port = 7070` | 磁盘变成版本 B，记录仍是 A |
| 4 | Agent 按旧计划调用 edit_file | 发现 B 与 A 不同，拒绝 |
| 5 | Agent 重新 read_file | 记录更新成 B |
| 6 | Agent 按新内容提交正确的替换 | 检查通过，写临时文件，再检查，发布 |
| 7 | 发布成功并验证 | 磁盘是新内容，记录更新到新版本 |

理解这张表，就能把读取、记录、检查、写入和错误恢复这几个部分串起来。保护范围和外部进程竞争窗口仍以前面的边界说明为准。
