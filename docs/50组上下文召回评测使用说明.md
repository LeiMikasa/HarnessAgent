# 50 组上下文召回与 token 评测

这套评测针对 HarnessAgent 的上下文压缩机制，比较 `full`（关闭压缩）和 `compact`（开启压缩）。无需 Langfuse，也不需要另一个付费模型评分。验收由 Python 检查实际产物。

## 用例设计

清单：[recall50.json](../evals/datasets/recall50.json)。共有 **50 个合成测试条件**，不是 50 道不同的真实编码题。每个场景组合五种信息位置和两种历史规模。

| 场景 | 数量 | 要检验的能力 |
| --- | ---: | --- |
| facts | 10 | 从分散的历史记录恢复六项准确值 |
| constraints | 10 | 保留路径、布尔值、整数、列表顺序等多条约束 |
| revisions | 10 | 找到最终批准的新值，忽略旧值和未批准的新提案 |
| distractors | 10 | 区分相似项目的记录及未批准的干扰值 |
| summary | 10 | 长普通消息触发模型摘要后，恢复准确值或检索完整归档 |

每例有 **6 项已知信息＋1 项没有提供的信息**。全量每组共有 300 个已知召回目标、50 个拒答目标。最终问题只指定项目和字段，不重复准确答案。信息的位置指字段组的起点；除 summary 场景外，六项信息还分散在不同历史分片，不能把起点当成每项的实际位置。

中等规模：20 组历史工具往返、每组约 2200 字符噪声；高规模：36 组、每组约 4000 字符噪声。摘要场景使用约 60000 / 120000 字符普通历史。**字符数只用于构造压力；用量统计来自真实 API usage，不用字符数估算 token。**

工具池、初始历史、最终问题、模型和运行预算在成对试验中一致，执行顺序交替。每次运行使用独立工作区和状态目录。团队、MCP、记忆和 shell 执行均关闭。目标答案和 Python 验收器在工具可访问工作区外；模型只能读取历史及压缩生成的归档，并写入 `answer.json`。

## 先运行免费检查

在项目根目录执行：

```powershell
# 只查看计划，不调用 API
.\.venv\Scripts\python.exe -m evals.recall50 --plan

# 免费完整流程检查：50 组 × 2 种模式 = 100 次 Mock Agent 运行
.\.venv\Scripts\python.exe -m evals.recall50 --provider mock
```

Mock 按预设答案驱动工具，用来验证压缩触发、产物验收、数据记录及报告生成。它知道脚本化答案，**Mock 的高召回率不代表模型能力，也不能用于简历效果数据**。Mock token 显示未知，不伪造用量。

## 真实模型运行

先确认 `.env` 已配置提供商、模型、端点和 API key。以下命令使用 DeepSeek 的项目配置。

```powershell
# 建议先跑五种场景各一例：5 组 × 2 = 10 次 Agent 运行
.\.venv\Scripts\python.exe -m evals.recall50 --provider deepseek --limit 5

# 全量：50 组 × 2 = 100 次 Agent 运行，默认每个条件只运行一次
.\.venv\Scripts\python.exe -m evals.recall50 --provider deepseek
```

**100 次 Agent 运行不是 100 次模型请求。** 每次可能经历多个工具轮次、摘要和恢复调用。真实运行会消耗 API 额度。默认每例每种模式最多 12 轮、单次主模型输出上限 4000 token、每例进程超时 240 秒；摘要使用生产压缩器自己的输出预算。SDK 内部重试的未返回用量无法完整获知。

可用 `--model` 指定模型、`--max-turns` / `--max-tokens` / `--timeout` 调整预算；两种模式始终使用同一组预算。可用 `--family summary` 或 `--ids facts-start-medium,revisions-middle-high` 指定子集。`--repeats 3` 是把同一条件重复三次，共 300 次 Agent 运行，不会变成 150 个不同用例。

## 指标如何计算

- **逐项准确召回率（micro_recall）**＝正确恢复的信息项数 / 全部已知目标信息项数。全量每组分母为 300。保持 JSON 类型，布尔值不能用数字代替，列表顺序不能变。
- **平均单例召回率（macro_recall）**＝各例召回率的平均值。本套每例都是六项，所以与 micro 相同；保留该指标便于后续扩展。
- **整例通过率（case_pass_rate）**＝完整通过的用例数 / 运行用例数。要求六项正确、未知项明确返回 null、无多余字段、格式正确，而且 Agent 正常结束。
- **正确拒答率（abstention_accuracy）**＝未知项正确返回 null 的次数 / 未知项目标数。单独统计，不把正确拒答当作召回信息。
- **失败处理**：超时、报错、未正常结束或无法解析 JSON 都按零项召回计入分母。有效 JSON 中的部分正确字段仍可计入逐项召回，即使整例没有通过。
- **token**：逐次保存原始 usage，包括主循环和摘要。分别累计 `input_tokens`、`output_tokens`、缓存写入与缓存读取；计数按供应商含义，不相加推断含缓存输入总数或费用。缺失任意调用的某字段，则该字段整组累计值和降幅为 null。
- **token 降幅**＝`(1 - compact / full) × 100%`，负数表示增加。报告同时提供全部运行和双方均通过配对的对比，避免把压缩组提前失败带来的低用量当作改善。

## 报告和续跑

结果保存在 `.scratch/evals/recall50-<时间>-<提供商>-<编号>/`：

| 文件 | 内容 |
| --- | --- |
| report.md | 可直接阅读的召回率、token 和分场景结果 |
| summary.json | 每例结果、全部统计、成对降幅及失败类型 |
| config.json / dataset.json | 运行预算、模型、端点和用例清单，均不记录 API key |
| repeat-*/<用例>/<模式>/case.json | 初始历史、问题、预期值，位于被测工作区之外 |
| repeat-*/<用例>/<模式>/result.json | 逐项验收、停止原因、原始 usage 和 token 累计 |
| repeat-*/<用例>/<模式>/telemetry.json | 每次调用后的用量检查点；超时只保留部分观测，不冒充完整用量 |

每完成一次运行就更新报告。退出码 1 表示至少一个用例失败，报告仍然有效。中途停止后，重复原来的参数并追加：

```powershell
.\.venv\Scripts\python.exe -m evals.recall50 --provider deepseek --resume .scratch\evals\recall50-实际批次目录
```

若原来用了 `--limit`、`--model` 或其他参数，续跑时也保留。已保存的结果（包括失败结果）不会重新调用模型；未完成工作区会保留为 interrupted 目录，新运行使用新工作区。模型、端点、预算、用例选择或评测代码变化时拒绝混合续跑。

## 如何报告结论

完整跑完后再写“50 组成对条件、100 次 Agent 运行”，并报告实际准确召回项数，如 `X/300`，以及整例通过数，如 `Y/50`。把真实模型和 Mock 结果分开。一次批次可以观察当前配置的表现，但不能证明总体成功率，也不能据此推断所有编码任务表现。

不要为了让召回率看起来合理而设定目标百分比或修改评分。即使两组都全通过，也应如实报告，并说明测试条件与样本限制。
