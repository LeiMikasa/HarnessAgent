# 执行范围与重复验证控制

这次修改针对一场实际运行：用户只要求分析项目，Agent 却安装依赖、连续跑两遍全量测试、复制项目并构建前端。第二遍全量测试的主要目的只是保存日志。

## 现在怎样处理

### 1. 分析和修改采用不同的完成标准

提示词明确要求：

- 分析、解释项目：默认阅读相关代码，给出结论，说明未运行验证的部分。
- 修改、修复项目：执行能验证本次变动的针对性检查，有具体原因再扩大范围。
- 可选检查缺少依赖，不自动演变成安装依赖、修复环境、复制整个项目。
- 达到交付要求后结束；无关问题作为后续建议。

同时，常见测试、构建、依赖安装命令必须提供 `task_reason`，解释为什么当前用户任务需要它。缺少理由，程序返回 `TASK_REASON_REQUIRED`，不启动进程。这是 Agent 必须交代执行依据，不要求用户逐次确认。

例如，用户要求修复一个函数时，可以提交：

```json
{
  "command": "python3 -m unittest discover -s tests -p test_example.py",
  "task_reason": "验证本次修复的输入边界和错误处理"
}
```

程序不能判断任意自然语言理由是否合理。任务范围由提示词和显式执行依据共同约束，这不是自动理解用户意图的完整权限系统。

### 2. 换超时设置或输出文件，不算新测试

每次 `run_loop` 创建独立的 `ExecutionGuard`。执行已识别检查前，它记录测试命令、调用者、工作目录、执行模式、Docker 容器和工作区内容摘要。

检查完成后，无论成功还是失败，都留下记录。同一轮请求内再次执行同一个检查，输入内容没有变化，会得到 `REPEATED_CHECK`，不会再次启动进程；错误会附带上一次保存的日志路径。

例如，下面两条命令的测试目标会被识别为相同：

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
timeout 900 python3 -m unittest discover -s tests -p 'test_*.py' > .scratch/run.log 2>&1
```

读取代码不会清掉记录。修改源文件、依赖清单后，可以重新验证。未知 shell 操作或依赖安装会让旧环境证据失效，避免错误声称环境没有变化。Docker 实际启动后的容器身份也会记录，换容器后可以重新验证。

若重复运行本身就是任务，例如调查偶发失败，可以填写 `rerun_reason` 说明原因。它是显式例外，不是新的人类审批流程。新的一轮用户请求也会重新开始记录。

### 3. 保存输出，不靠再次执行补日志

被识别的检查，以及提供了 `task_reason` 的其他命令，会在输出被截断前，把捕获的 stdout、stderr 和退出状态保存到当前 Runtime 的状态目录：

```text
<state_dir>/command-logs/<唯一编号>.log
```

普通 CLI 通常位于项目的 `.agent` 下；Web 会话使用各自的 Runtime 状态目录。工具结果返回绝对日志路径，可以用 `read_file` 继续读取。

这里保存的是工具捕获到的输出。如果命令自己把输出重定向到了另一个文件，那部分内容仍在命令指定的文件里。建议直接执行检查，让工具自动保存。日志落盘失败会报告，但不会把失败检查改报成功。宿主机超时异常携带的部分输出也会保存；Docker 超时若没有提供输出，则不能恢复容器里未返回的内容。

### 4. 不允许后面的命令掩盖检查失败

对识别到的测试、构建、检查，下面这类写法会在执行前返回 `CHECK_STATUS_MASKED`：

```bash
python3 -m unittest discover; echo done
npm test | tail -30
pytest || echo ignored
```

程序要求直接执行检查，保持退出状态可信。没有根据输出中的“失败”字样猜结果，也没有偷偷重写用户命令。

## 实现位置

| 文件 | 作用 |
| --- | --- |
| `agent/prompt.py` | 明确分析与修改的范围、停止条件和日志使用方式 |
| `agent/tools/execution.py` | 执行理由检查、命令归一化、工作区摘要和重复检查拦截 |
| `agent/loop.py` | 每轮创建独立检查器，接入执行前与执行后流程，并记录拦截事件 |
| `agent/tools/basic.py` | Bash 参数、执行状态检查、完整捕获输出落盘 |
| `agent/tools/feedback.py` | 常见检查命令识别，包含 Python `-X`、`-W` 等解释器选项 |
| `agent/tools/result.py` | 在内部工具结果中保留日志位置，供重复检查提示使用 |
| `agent/shell.py` | 告知模型检查应直接执行、输出自动保存 |
| `tests/test_execution_guard.py` | 覆盖实际事故、代码变动后复验、权限、超时、Docker 和日志失败 |

## 实际边界

- 这是效率控制，不是 shell 安全沙箱。现有权限检查仍然负责授权。
- 识别常见的 Python、Node 工具命令，不执行自定义脚本来判断它内部是否跑测试；复杂 shell 包装也可能无法识别。
- 归一化保留测试选择器、解释器、环境变量和目录区别；不会把所有测试都当成同一件事。
- 摘要跳过依赖目录、Git、运行状态、构建目录和日志等生成内容。它不证明外部服务、数据库或依赖目录从未变化；确实需要时可填写复跑理由。
- 摘要最多处理 4,000 个文件、16 MB 内容；超过限额、遇到符号链接或读取异常时不拦截重复，避免依据不完整的快照误判“没有变化”。
- 没有强行限制任务只能运行几分钟，也不会因为一次失败就结束需要修复的任务。

## 验证

新增回归覆盖：缺少执行理由、退出状态被掩盖、超时与重定向归一化、成功和失败检查去重、源文件与依赖清单变动、环境变动、显式偶发问题调查、完整日志与日志失败、超时、懒加载 Docker、权限拒绝以及跨请求隔离。

其中还真实启动一个只有一个失败用例的小型 unittest，确认退出码为失败，并且日志保留断言信息。没有为本次修改运行项目全量测试，也没有调用真实模型做效果对比。

本轮运行上述新增用例及相关已有模块，共 120 个用例：119 个通过，1 个因平台条件跳过。当前项目的工作区摘要可正常生成，单次实测约 0.1 秒。
