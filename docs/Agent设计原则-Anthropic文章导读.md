# Agent 设计原则：Anthropic 文章中文导读

来源：[Building effective agents — Anthropic](https://www.anthropic.com/engineering/building-effective-agents)。原文发表于 2024 年 12 月 19 日；当前页面提示部分工具信息已有变化。

本文先简要转述原文，再用 HarnessAgent 的代码举例。项目建议和例子属于结合当前工程的解读，不是原文结论。

## 1. 原文的核心原则

- **先简单，再复杂。** 先尝试单次模型调用，只有评测证明收益才增加步骤和机制，同时衡量成本与耗时。
- **按任务选择控制方式。** Workflow 由代码规定路线；Agent 由模型决定下一步。步骤固定时用前者，路线难预测时考虑后者。
- **理解底层过程。** 框架可以省事，但开发者仍需知道提示词、响应和工具如何执行。
- **重视工具接口。** 说明写清用途、参数、示例和边界，并通过测试减少误用。
- **依赖环境反馈。** 用工具返回和代码执行结果判断进展，同时明确停止条件、人工介入点，在沙箱中测试。
- **保持透明。** 让行动计划和执行过程可理解，便于检查和调试。

原文介绍的常用工作流如下；它们是可组合的模式，不是必须逐级实现的等级。

| 模式 | 如何工作 |
| --- | --- |
| 提示链 | 固定步骤依次执行，中间可加检查 |
| 路由 | 分类后交给相应处理流程 |
| 并行 | 独立任务同时做，或多次判断后汇总 |
| 协调者与执行者 | 模型动态拆任务、委派并汇总 |
| 评估与优化 | 生成结果，再依据评价反复改进 |

## 2. 放到你的项目里，分别是什么意思

下面是针对 HarnessAgent 的工程解读。

### 统一循环负责推进，模块负责提供能力

你的 `agent/loop.py` 已经围绕一个循环组织：请求模型 → 执行工具 → 回传结果 → 再请求模型。`runtime.py` 负责接线，压缩、权限和目标检查分别由模块实现。

可以把它理解为：循环负责让车继续行驶，外围模块分别负责导航、刹车和仪表。新增机制时，先说明它解决哪个已观察到的问题，再决定它应挂在哪里。

### “知道怎么做”与“允许怎么做”分开设计

例如模型决定先读取哪个文件，这是任务策略；文件能否越过工作区边界，是宿主权限规则。提示词可以告诉模型边界，工具层仍要执行检查。

你项目里的 `permissions.py`、`safe_path()` 和调用前的权限清理就是适合验证的边界。测试应故意尝试越界，检查工具是否阻止操作。

### “模型说完成”需要与“产物通过验收”分开记录

例如 CSV 解析器写完了，模型可能给出“已完成”。但是否正确，还要检查末尾空字段、转义引号、非法引号等情况。

你已有的外部验收脚本能直接检查产物。`goal.py` 则让另一轮模型调用判断目标是否达成：它可以帮助续做任务，但自己的判断也需要与独立验收对照，测量误判。

### 工具设计要考虑实际误用

一个文件编辑工具至少应让模型知道：路径相对于哪个目录、旧内容是否必须唯一匹配、匹配失败会返回什么，以及失败后文件是否已经改变。

尤其要测试队友认领任务后目录发生切换的情况。你已有的 worktree 上下文测试，比只检查工具说明文字更能证明目录切换是否正确。

这里的“透明”可以落实为行动计划、调用状态、错误和验收证据；不需要展示模型的内部推理全文。

## 3. 一个具体例子：修复 CSV 解析器

假设用户要求修复末尾空字段丢失的问题。可以这样组织一次任务：

1. **说明验收条件：** 输入 `a,b,` 应输出三个字段，最后一个是空字符串。
2. **取得证据：** 读取实现，运行能够复现缺陷的检查。
3. **修改代码：** 由模型根据当前结果选择下一步工具调用。
4. **验证产物：** 执行工作区外的验收，检查其他边界情况是否仍正确。
5. **决定继续或结束：** 失败时回传具体用例；通过时报告验证结果。达到预设轮数或时间预算时明确返回当前状态。

这组验收步骤可以由代码固定安排；修复过程中如何调查、修改和重试，则可以由 Agent 决定。一个应用里可以同时存在这两种控制方式。

## 4. 你当前的压缩评测应回答什么

结合项目现状，建议把“减少输入”与“仍能完成任务”同时测量：

| 问题 | 对应指标 |
| --- | --- |
| 关键信息还找得到吗？ | 准确值召回率，按信息位置分别统计 |
| 编码结果仍正确吗？ | 工作区外的独立验收通过率 |
| 用量是否减少？ | 供应商报告的输入、输出和缓存 token，包含摘要调用 |
| 是否引入额外开销？ | 总耗时、摘要次数、归档检索次数 |
| 压缩真的发生了吗？ | 压缩事件和归档产物 |

保持模型、任务、初始历史和预算一致，仅切换压缩。Mock 用来检查评测流程；真实模型运行才用于观察任务效果。历史批次只有字符计量，新接入的 `usage` 统计用于后续运行，不能补回旧批次的 token。

## 5. 下一次增加机制前，先写下这四件事

1. **问题：** 当前系统在哪类任务上失败？
2. **方案：** 这个机制具体改变哪个行为？
3. **证据：** 用什么对照和验收证明改善？
4. **代价：** 增加多少调用、耗时和维护负担？

例如，“需要多 Agent”还不够具体；“两个独立文件可以并行实现，团队模式在同一验收下是否缩短耗时”才是可以实验验证的问题。
