# 命令执行与失败诊断

本次调整针对真实 Vue 项目运行中出现的 Windows 命令不兼容、中文乱码，以及失败后反复调试。

## 执行环境

`bash` 是工具名称。Windows 上实际使用 `COMSPEC` 指向的 Shell（通常为 cmd.exe），POSIX 上使用 `/bin/sh`。
不根据交互终端的 `$SHELL` 猜测执行方式，也不把 cmd 语法当作 PowerShell 语法。

主系统提示词和 bash 工具描述会给出平台、Shell 及相应注意事项。子 Agent、队友共用的基础工具也携带这段描述。
Windows 下提醒模型不要假设 `tail` 等 Unix 工具存在；复杂的 JavaScript/Python 调试逻辑优先写成工作区脚本，再调用解释器运行。

## 输出与编码

命令输出先捕获为字节，再分别解码 stdout、stderr：

1. 识别带 BOM 的 UTF-16。
2. 优先尝试 UTF-8（含 BOM）。
3. Windows 上尝试 OEM、ANSI 编码，再尝试系统区域编码。
4. 无法正确解码时用替换字符兜底，避免解码错误导致整个工具异常。

子进程环境是父环境的副本；没有显式设置 `PYTHONIOENCODING` 时，为 Python 子进程默认提供 UTF-8，不改写父进程环境，也不覆盖已有设置。
没有 BOM 的编码只能按这些规则判断；同一输出流混合多种编码时仍可能出现乱码，不能保证识别任意编码。

成功命令保留原来的普通文本返回方式。失败命令在原有 `COMMAND_FAILED` 结构化错误中显示：

```text
Error: Exit code: 1
stdout:
检查开始
stderr:
AssertionError: expected 12, actual 11
```

失败输出在约 50000 字符预算内分配两条流的空间，避免超长 stdout 把 stderr 完全挤掉。
命令失败仍保留 `execution_status=unknown`，因为失败前可能已经写过文件；程序不会自动重试 bash。

## 下一轮的诊断提醒

`run_loop` 为每个执行循环创建独立的 `CommandFeedback`。
收到 `COMMAND_FAILED` 后，在下一次模型调用的 system 提示词末尾附加短提醒：

- 从退出码、stdout、stderr 找出失败步骤。
- 检查失败断言、相关实现和预期值/实际值。
- 根据证据修复，保留有意义的验收，不为通过而删除或放宽检查。
- 重跑前检查可能产生的副作用；复杂调试使用脚本文件。

若 bash 参数及返回给模型的可见错误完全相同，连续出现两次，就再提醒先做针对性检查或更换诊断方法。
这比较的是可见结果，不证明截断窗口之外的完整错误相同。成功的 bash、不同参数/错误，或其他潜在修改工具调用会重置重复计数；只读检查不被当作文件修改。
外部进程的修改不能被完整追踪，因此提醒是建议，不用于阻断命令。

每批工具只形成一条有界提醒，不新增用户消息、不增加模型调用、不自动执行工具。
后续一批没有命令失败时，提醒清除；新用户请求和子 Agent 的循环各自重新计数。
权限拒绝、参数错误与超时继续使用原有的恢复反馈，不套用“检查断言”的建议。
日志记录 `command_feedback` 事件和重复次数，不额外保存命令或错误正文。

## 验证方式与边界

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_command_diagnosis.py -v
```

测试使用 Mock 模型与真实本地命令，覆盖中文输出、双流截断、编码回退、失败修复、重复提醒及循环间隔离。
它们可以证明反馈流程和执行兼容性，不能证明真实模型一定采纳提醒，或真实任务轮数一定减少；后者需用真实运行对照验证。
