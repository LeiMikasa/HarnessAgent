### 1. 用一分钟介绍你的项目

> HarnessAgent 是用 Python 实现的编码 Agent 执行框架。模型负责选择下一步动作，框架负责执行工具、回传结果、保存状态和控制权限。主 Agent、一次性子 Agent、持续工作的线程队友复用同一个核心循环。

### 2. Agent、普通模型调用、Workflow 有什么区别？

**参考回答：** 单次模型调用主要产生一次输出。Workflow 的主要步骤由代码预先确定；Agent 则根据任务与工具反馈动态选择动作。比如“读取代码 → 固定执行检查 → 固定输出结果”可以是工作流；“发现错误后决定查哪个文件、改哪里、是否继续测试”体现了 Agent 决策。

**项目对应：** 本项目代码固定了权限、工具执行和循环边界，但具体工具名称与参数由模型返回。这是受框架约束的动态执行，并不意味着模型拥有任意执行权限。

**可能追问：** 为什么不用固定流程？步骤稳定、验收明确时，固定流程通常更容易控制；代码探索路径不固定时，动态工具选择更有用。选型需要结合任务与评测。

### 3. ReAct 在项目里怎样体现？

**参考回答：** 可以理解为模型根据当前信息选择行动，工具提供新的观察结果，然后模型再决定下一步。

```text
用户：修复一个函数
模型：调用 read_file
框架：执行读取，返回文件内容
模型：根据内容调用 edit_file
框架：返回修改结果
模型：调用测试工具，再根据测试结果继续或结束
```

**项目对应：** `run_loop()` 把模型输出中的 `tool_use` 交给执行器，再将对应的 `tool_result` 加入消息历史。模型提出动作，Python 执行真实动作。这里只能依据可观察的工具与反馈说明行为，不能据此声称掌握了模型内部全部推理过程。

**代码依据：** [loop.py](D:/HarnessAgent/agent/loop.py)。

### 4. 为什么手写 Harness，而不是直接套框架？

**参考回答：** 本项目选择直接实现循环，便于理解和验证消息配对、权限、压缩、动态工具池这些机制。`Runtime` 组装服务，`Loop` 负责调度，`Registry` 分发工具，`Hooks` 在调用前后和结束时接入策略。

**取舍：** 代码路径直接，但需要自己维护协议兼容、可靠性和评测。项目采用这个设计，不等于已经通过对照实验证明它优于现成框架，也不能因此声称做过 LangGraph 的生产实践。

**代码依据：** [runtime.py](D:/HarnessAgent/agent/runtime.py)、[registry.py](D:/HarnessAgent/agent/tools/registry.py)、[events.py](D:/HarnessAgent/agent/events.py)。

### 5. 如何避免无限循环、过早结束和执行半截工具调用？

**面试表达：**

> 我把执行控制分成总预算、响应完整性检查和停止检查三层。总轮数上限防止任务无限执行；对于空响应、只有思考内容或被截断的回答，框架不会当成完成，而是有限恢复。工具响应如果因为输出上限被截断，我会丢弃当前响应的整批调用，避免执行不完整参数，同时保留此前已经完成的操作。模型提出结束后，还会经过 Stop Hook；设置了目标条件时，评估器可以根据工具证据要求继续。最后，我把“循环正常结束”和“任务验收通过”分开，真正的评测结果由独立评分器或测试决定。

**先理解正常执行路径。** 用户要求“修复 add.py 并测试”时，可能依次经历读取、修改、运行测试和最终回答。每次工具调用的结果都会进入消息历史，供下一轮模型决策。模型返回后，循环先提取工具调用与普通文本，再决定执行、恢复或结束：

```python
calls = tool_use_blocks(response.content)
final_text = extract_text(response.content).strip()
provider_stop = response.stop_reason or "unknown"
```

这三项分别表示“模型想执行什么”“模型回答了什么”和“供应商为什么停止生成”。见 [响应解析](D:/HarnessAgent/agent/loop.py:195)。

**机制一：总轮数限制，防止一直运行。**

```python
for turn in range(1, max(1, max_turns) + 1):
    ...
```

每次进入循环都占用一轮，包括正常执行、不完整响应恢复、超限恢复和 Stop Hook 要求继续。普通运行默认 150 轮；50 用例评测默认 12 轮。预算耗尽后返回 `stop_reason="max_turns"`，不会因为“没有再继续”就认定任务完成。

当前没有通用的“连续重复同一动作就停止”检测，而是依靠轮数上限兜底。轮数上限也无法单独处理一个迟迟不返回的请求，仍需请求超时；评测脚本额外设置了默认 240 秒的单次运行超时。

代码位置：[循环预算](D:/HarnessAgent/agent/loop.py:148)、[耗尽后的返回](D:/HarnessAgent/agent/loop.py:307)、[普通配置](D:/HarnessAgent/agent/config.py:119)。

**机制二：空响应和截断文本不能直接当成完成。**

```python
if not calls and (not final_text or provider_stop == "max_tokens"):
    ...
```

没有工具调用且没有普通文本，意味着既没有动作，也没有最终回答。只有 thinking 内容也会落入这个分支。已有普通文本但以 `max_tokens` 结束，则可能只回答了一半。两类情况都不会直接触发正常停止，而是加入恢复提示，要求模型给出具体动作或继续回答。

已有截断文本时，保存这段响应并追加“回答被截断，请继续”的消息；空响应或只有思考内容时，不把该响应加入历史，避免继续发送无效内容。

不完整响应最多恢复 2 次：第一次失败后重试，第二次失败后再重试，第三次仍不完整就返回 `error`。这是**连续不完整响应**的预算，获得正常响应后 `incomplete_retries` 清零；不是整个任务只能重试两次。若总轮数先耗尽，则先按 `max_turns` 结束。

代码位置：[不完整响应处理](D:/HarnessAgent/agent/loop.py:232)、[恢复计数清零](D:/HarnessAgent/agent/loop.py:257)。

**机制三：截断工具响应整批不执行。**

```python
if calls and provider_stop == "max_tokens":
    ...  # 不执行这一响应的调用，进入有限恢复
```

工具参数可能只生成了一部分，所以即使响应里已有 `tool_use`，也不能直接执行。框架丢弃该响应里的全部调用，不把它们加入历史，并在下一轮系统提示里说明“这批调用没有执行，请重新生成一个小而完整的调用”。恢复提示要求拆分大文件写入或修改，避免模型误以为被丢弃的动作已经成功。

例如上一轮成功修改了 a.py，这一轮准备修改 b.py 和 c.py，但响应被截断：a.py 的修改保留，这一轮对 b.py、c.py 的调用都不执行。它是在拒绝当前不完整动作，并没有回滚之前已经执行的操作。

这一分支与空响应、截断文本共用 `incomplete_retries`，并不是每种错误各有两次恢复机会。正常响应后，恢复计数与恢复提示一起清空。

代码位置：[截断工具调用处理](D:/HarnessAgent/agent/loop.py:207)。已有 [恢复测试](D:/HarnessAgent/tests/test_incomplete_response.py) 覆盖整批不执行、此前成功操作保留及恢复预算共享等情况。

**机制四：模型提出结束后，经过 Stop Hook。**

只有响应通过完整性检查且没有工具调用，循环才触发：

```python
forced = hook_registry.trigger(STOP, messages)
```

Stop Hook 是结束前的检查入口，可返回继续原因，或要求以特定状态结束。它不是一个自动证明任务正确的模块。

| Hook 的结果 | 循环的处理 |
| --- | --- |
| 不拦截 | 返回 `final`，正常结束 |
| 要求继续 | 将原因作为 user 消息加入历史，进入下一轮 |
| 要求特殊状态返回 | 返回对应状态，例如 `goal_error` 或 `goal_limit` |

主 Runtime 注册了目标检查与记忆提取。目标检查可以要求继续；记忆提取主要保存长期信息。目标检查先运行，若要求继续或特殊返回，会截断后续 Hook。

**目标评估只有设置了 `/goal` 才启用，普通请求不会自动进行模型目标验收。** 例如设置 `/goal 修复 add.py，并提供测试通过的证据` 后，主模型回答“完成了”，评估器会另发一次不带工具的模型请求，查看目标和近期消息中的工具记录。

如果它判断尚无测试证据，框架会把“还缺测试证据，请继续工作”反馈给主模型。若判定达成，就允许正常结束。目标续跑默认每次用户请求最多 8 次；达到上限或评估出错时返回对应状态。队友仍在执行相关任务时，会暂缓判断并以 `goal_defer` 返回，同时保留目标。

边界是：评估器也是模型，判断依据还是当前可见的历史，可能误判或缺少证据，不能替代独立测试。

代码位置：[停止分支](D:/HarnessAgent/agent/loop.py:262)、[Hook 安装](D:/HarnessAgent/agent/runtime.py:237)、[目标 Hook](D:/HarnessAgent/agent/runtime.py:313)、[目标判断与续跑上限](D:/HarnessAgent/agent/goal.py:136)。

**机制五：输入上下文超限，走应急压缩恢复。**

`max_tokens` 通常表示响应达到输出上限；上下文超限则是请求的输入历史过长，两者不能混为一谈。每轮调用前先执行 `compactor.prepare()`；若供应商仍报上下文超限，就捕获异常，进行应急压缩并进入下一轮请求。

连续超限最多允许 1 次应急恢复，压缩后仍失败就返回 `error`。成功获得响应后，应急计数清零。这条路径和不完整输出的恢复计数相互独立，但都使用同一个总轮数预算。

代码位置：[调用前压缩](D:/HarnessAgent/agent/loop.py:157)、[应急恢复](D:/HarnessAgent/agent/loop.py:180)。

**最后区分执行结束、验收成功和成本控制。**

`LoopResult.ok` 的实现只判断 `stop_reason == "final"`，说明循环正常结束，不说明答案或代码正确。例如正常写出 answer.json，但 6 个字段只答对 4 个，循环可以正常结束，用例仍然失败。

评测脚本因此单独运行评分器，并要求两个条件同时满足：

```python
grading = grade_answer(workspace, case)
result["success"] = loop.ok and grading["passed"]
```

另外，`max_tokens` 控制单次模型响应的输出预算；`max_turns` 控制循环轮数。摘要、目标评估和 SDK 内部重试可能增加模型请求，输入长度也在变化，所以它们不能直接当作整个任务的精确 token 或金额上限。记录 usage 是消耗统计，不等于已经实现了达到累计成本阈值就强制停止。

代码位置：[LoopResult.ok](D:/HarnessAgent/agent/loop.py:54)、[独立验收](D:/HarnessAgent/evals/recall50.py:133)。

## 二、工具、协议与权限

### 6. Function Calling 的完整流程是什么？模型会自己执行 Python 吗？

**参考回答：** 框架把工具名称、描述和参数 Schema 发送给模型；模型生成调用名称和参数；宿主程序检查权限并调用函数；执行结果带着调用 ID 返回模型。模型生成的是调用请求，真正执行由宿主完成。

**项目对应：** `registry.definitions()` 提供工具定义，`execute_tool()` 走调用前 Hook、工具执行、调用后 Hook，`make_tool_result()` 构造反馈。

**可能追问：** 一个响应包含多个工具怎么办？当前循环逐个执行，再把这一批结果一起追加回历史，不是自动并行执行所有工具。

**代码依据：** [loop.py](D:/HarnessAgent/agent/loop.py)、[registry.py](D:/HarnessAgent/agent/tools/registry.py)、[llm.py](D:/HarnessAgent/agent/llm.py)。

### 7. 工具参数错误、工具名不存在或执行失败怎么办？

**参考回答：** 项目现在先统一执行 JSON Schema 参数校验，再检查权限并执行工具。失败结果带明确的错误码、字段、恢复动作和执行状态，并以 `is_error=true` 回传模型。参数错误要求模型修正；原文或路径不匹配要求先检查实际信息；只读且经宿主明确允许重试的工具，遇到指定暂时性故障最多执行 3 次，包含首次执行。

**具体策略：**

| 情况 | 实际恢复动作 |
| --- | --- |
| 缺少字段、类型或范围错误 | 不执行工具，反馈错误字段，模型修正参数 |
| 找不到文件或修改原文 | 不原样自动重试，提示读取、查找并依据实际状态修改 |
| 允许重试的只读工具发生暂时性故障 | 工具层最多重试 2 次，指数退避加随机等待，每次重新检查权限 |
| 权限拒绝、未分类错误或 MCP 业务错误 | 不自动重试，返回明确失败 |
| 文件写入结果未知 | 反馈检查状态，并阻止本轮再次写入或修改同一文件；完整且未截断的读取，或实际确认文件不存在后解除检查门槛 |
| 同一工具、同一目标的可修复错误持续出现 | 初始失败后给两次修正机会，再调用时返回恢复预算耗尽；成功后清除该目标计数 |

**项目细节：** 修复预算属于当前 `run_loop`，主 Agent、子 Agent 与队友的循环分别管理。读取文件不会清除失败修改的修复预算；它只能解除写入结果未知的状态检查门槛。一次用户请求结束后不沿用旧预算。每次尝试记录错误码、耗时和是否自动重试，50 用例评测结果中也保存 `tool_attempts`。

**边界：** `read_only` 本身不足以开启重试，还需宿主设置 `retry_safe`；MCP 服务自己的只读声明不作为授权。普通字符串保持文本兼容，不能通过匹配 `Error:` 猜测失败；新增工具应明确返回 `ToolResult` 或抛出 `ToolError`。文件完整读取只证明状态已经供模型检查，不证明写入内容正确。超大文件无法一次完整读取时不会自动解除门槛。`bash` 不自动重试，其副作用仍需要根据具体命令人工或模型检查。当前没有通用幂等、事务回滚或跨会话的不确定状态恢复。

**面试表达：** 我把参数修正和执行重试分开：参数错了，反馈给模型修改；暂时性故障，只有明确允许安全重复的只读工具才有限重试。对写操作保持保守，结果未知时先检查实际文件状态。模型反复修错也有独立预算，全部仍受总循环轮数限制。我通过故障注入验证恢复成功、预算耗尽、权限拒绝和副作用不重复。

**代码依据：** [registry.py](D:/HarnessAgent/agent/tools/registry.py)、[result.py](D:/HarnessAgent/agent/tools/result.py)、[recovery.py](D:/HarnessAgent/agent/tools/recovery.py)、[loop.py](D:/HarnessAgent/agent/loop.py)、[故障测试](D:/HarnessAgent/tests/test_tool_recovery.py)。

### 8. Skills、MCP 和普通工具是什么关系？

**参考回答：** 普通工具是可执行函数；Skill 是说明某类任务如何做的操作指南；MCP 是接入外部工具服务的协议。加载 Skill 不会自动执行代码，连接 MCP 也不意味着新工具可以跳过权限检查。

**项目对应：** Skill 名称和描述进入系统提示词，需要时通过 `load_skill` 把正文加入上下文。MCP 支持进程内示例服务和 stdio 服务，连接后将工具注册到同一个工具池。循环每轮重新读取工具定义，因此模型下一轮可以看到刚连接的工具。

**边界：** Skill 的“按需”指正文进入模型上下文的时机；启动扫描时已经读取并缓存正文。当前支持的 MCP 传输范围也不能表述成兼容所有远程服务。

**代码依据：** [skills.py](D:/HarnessAgent/agent/skills.py)、[mcp.py](D:/HarnessAgent/agent/mcp.py)、[loop.py](D:/HarnessAgent/agent/loop.py)。

### 9. 怎样控制危险操作？权限系统是不是沙箱？

**参考回答：** 不能只在提示词里要求模型安全。项目在工具执行前通过权限 Hook 检查拒绝列表、规则和必要的审批；文件工具另用 `safe_path` 检查实际路径是否留在工作区内。一次越界批准只作用于一次调用，避免授权泄漏。

**边界：** 规则与字符串检查不是操作系统级沙箱。特别是通用 shell 工具，不能依赖几条规则防住任意命令。进程、网络与文件系统隔离属于进一步的工程工作，不能说当前项目已经全部实现。

**代码依据：** [permissions.py](D:/HarnessAgent/agent/permissions.py)、[basic.py](D:/HarnessAgent/agent/tools/basic.py)、[loop.py](D:/HarnessAgent/agent/loop.py)。

## 三、上下文压缩与记忆

### 10. 为什么需要压缩？五级压缩具体做什么？

**参考回答：** 编码任务的日志、文件内容和工具结果会持续增长。项目按照先确定性处理、后生成摘要的顺序腾出空间：

1. 对最新一批超大工具结果做磁盘持久化，保留预览。
2. 历史消息过多时，归档中间部分，保留开头、近期消息和存档地址。
3. 字符量仍过大时，把已读旧工具结果替换为文件指针。
4. 仍超限时，进一步缩短最大的工具结果，包括必要时缩短尚未读过的大结果。
5. 最后才调用模型生成摘要，保留当前请求和完整存档地址。

这些阶段不是每次全部执行。代码按消息数、字符量和结果大小决定是否触发。正常准备仍未挡住供应商超限时，还有应急压缩路径；模型也可以主动请求 `compact`。

**取舍：** 优先避免额外摘要调用，但磁盘指针需要后续查找；摘要更紧凑，却可能遗漏信息。两者都需要评测。

**代码依据：** [context.py](D:/HarnessAgent/agent/context.py)。

### 11. 内容写到磁盘后，模型如何找回来？这算 RAG 吗？

**参考回答：** 压缩后的消息里保留原文路径。模型发现摘要不足时，可以调用 `read_file` 或 `grep`；框架执行读取，把内容作为工具结果返回，然后模型继续回答或工作。文件地址只是线索，模型仍需要决定是否查找。

**例子：** 摘要只说“已经确定发布配置”，但没有端口。模型读取存档，找到 `api_port=8508`，再输出答案。该读取之后的模型请求也消耗 token。

**边界：** 当前是磁盘归档与工具查找，不包含向量索引、Embedding、Reranker 等完整向量 RAG 链路。存档存在只能证明原文可访问，不能保证每次准确召回。

**代码依据：** [context.py](D:/HarnessAgent/agent/context.py)、[basic.py](D:/HarnessAgent/agent/tools/basic.py)。

### 12. 压缩为什么要保护 `tool_use` 与 `tool_result`？

**参考回答：** 两者通过 ID 对应。删掉调用但留下结果，会出现没有来源的结果；删掉结果却留下调用，会出现没有完成的调用。归档边界要调整到完整的工具交互处。

**项目细节：** 中间归档和应急压缩会检查边界；微压缩优先处理模型已读的旧结果，避免过早藏起新反馈；主动 `compact` 等整个工具批次执行并记录结果后才进行。

**可能追问：** 同批次先 `write_file` 再 `compact` 为什么不能立即压缩？因为修改结果还没进入历史，摘要可能不知道文件已改。应先完整记录本批次副作用和结果。

**代码依据：** [context.py](D:/HarnessAgent/agent/context.py)、[loop.py](D:/HarnessAgent/agent/loop.py)。

### 13. 压缩和长期记忆有什么区别？怎样避免保存临时信息？

**参考回答：** 压缩管理当前会话的容量；长期记忆选择跨会话仍有用的信息。比如“用户长期偏好中文回答”可能值得保存，“这次临时用某个端口”通常只属于当前任务。

**项目对应：** 记忆模块包含选择、提取和整合。新请求选择相关记录，本轮缓存选择结果；回合结束提取候选；需要时整合记录。候选区分 `persistent` 与 `current_task`，程序还检查临时表达、字段和重复内容。选择失败时可以回退到关键词匹配。

**边界：** 过滤和归一化去重并不保证消除所有错误事实与语义重复。若后续改进，可增加来源、更新时间、冲突处理与过期规则；不能把这些后续设计说成现有能力。

**代码依据：** [memory.py](D:/HarnessAgent/agent/memory.py)、[runtime.py](D:/HarnessAgent/agent/runtime.py)。

## 四、多 Agent 与并发

### 14. 子 Agent 与线程队友有什么区别？如何隔离上下文？

**参考回答：** 子 Agent 是一次性委派，使用新的消息历史完成任务，再把结果带回主 Agent；线程队友保留自己的消息历史，通过信箱与任务板持续工作。两者复用核心循环，差异在生命周期、工具池和状态。

**例子：** 让子 Agent 调查某个模块，可以避免主 Agent 常驻全部搜索日志；把两个独立模块交给两个队友，可以让它们各自维护执行上下文。

**边界：** 独立消息历史不代表独立文件系统。写文件隔离还要依赖工作目录、工具权限和分配的 worktree。

**代码依据：** [subagent.py](D:/HarnessAgent/agent/subagent.py)、[teams.py](D:/HarnessAgent/agent/teams.py)、[runtime.py](D:/HarnessAgent/agent/runtime.py)。

### 15. 两个队友同时认领同一个任务怎么办？

**参考回答：** `TaskStore.claim()` 在进程内同一把 `RLock` 下检查状态、所有者和依赖，再更新任务。文件通过临时文件加 `os.replace` 写入，避免读到半写的数据。

**关键区别：** 锁保证同一进程线程间的“检查并更新”不被打断；原子文件替换保证文件写入完整。原子替换本身不能阻止两个进程同时读旧状态后分别覆盖。

**可能追问：** 扩展到多个进程或机器怎么办？需要数据库事务、条件更新或其他跨进程协调方案。当前实现不能直接声称具有分布式一致性。

**代码依据：** [tasks.py](D:/HarnessAgent/agent/tasks.py)、[teams.py](D:/HarnessAgent/agent/teams.py)。

### 16. 多 Agent 一定更快吗？什么任务值得拆分？

**参考回答：** 不一定。任务独立、单个子任务足够大、结果容易验收时，并行可能抵消调度与汇总开销；任务很短、互相依赖或频繁修改同一个文件时，协作可能更慢、更费 token。

**项目对应：** 有任务依赖图、信箱和 worktree 管理，也有单 Agent 与团队的速度评测脚本。证明收益必须固定任务与验收标准，比较成功率、耗时和资源消耗。

**边界：** 当前 `team_speed.py` 尚未汇总整个团队的 token 用量，不能仅因为底层响应带 `usage`，就声称团队评测已经完成成本统计。

**代码依据：** [teams.py](D:/HarnessAgent/agent/teams.py)、[tasks.py](D:/HarnessAgent/agent/tasks.py)、[team_speed.py](D:/HarnessAgent/evals/team_speed.py)。

## 五、评测：这是目前最值得准备的部分

### 17. Mock 为什么能达到 100%？能写进简历吗？

**参考回答：** 这套召回评测的 `SuiteMockLLM` 使用预设的标准答案输出。它用于检查工具执行、答案落盘、评分、成对汇总和报告流程，不是在模拟真实模型的理解与召回能力。

**可以证明：** 流程能跑通、评分能识别指定错误、缺失 token 不会被当成 0。

**不能证明：** 模型召回率 100%、题目足够难、压缩没有质量损失。离线测试与真实模型效果评测要分别表述。

**代码依据：** [recall50.py](D:/HarnessAgent/evals/recall50.py)、[test_recall50.py](D:/HarnessAgent/tests/test_recall50.py)。

### 18. 50 个用例怎么构建？模型能不能看到标准答案？

**参考回答：** 一套数据集包含 50 个条件，由 5 类场景 × 5 种位置 × 2 档历史压力组成：普通事实、约束、版本更新、相似记录干扰、长文本摘要。每个用例有 6 个已知目标和 1 个无已知值的问题。

生成器根据用例 ID 确定性生成项目与字段值，再把正确记录和必要的干扰记录放进模拟历史。最终问题只列字段和选择规则，不重复正确值。标准答案与评分器放在 Agent 工作区之外；真实运行只开放限定工作区的文件工具。

**位置含义：** 起始位置控制记录组的锚点，单个字段会分散到不同历史片段；不是每一条信息都集中在同一个位置。

**边界：** 这是 50 个模板生成条件，不是 50 个来自真实用户的独立编码任务。版本题按最高已批准 revision 判断，也不是简单选择历史中最后出现的值。

**代码依据：** [recall_cases.py](D:/HarnessAgent/evals/recall_cases.py)、[recall50.json](D:/HarnessAgent/evals/datasets/recall50.json)。

### 19. 召回率、通过率和 token 节省比例分别怎么算？

**参考回答：** 这套评测将“已知目标值恢复正确的比例”称为召回率，采用字段值与 JSON 类型的严格比较。它不是向量检索系统的 Recall@K。

| 指标 | 当前计算方式 | 假设例子 |
| --- | --- | --- |
| 单用例召回率 | 正确恢复的已知项数 / 6 | 5/6 ≈ 83.3% |
| 每组整体召回率 | 正确已知项总数 / 已知项目标总数 | 完整 50 个用例中 240/300 = 80% |
| 用例通过率 | 全部要求通过的运行数 / 总运行数 | 35/50 = 70% |
| 未知信息正确处理率 | 正确输出 null 的未知项数 / 未知项目标数 | 45/50 = 90% |
| 输入 token 节省比例 | 1 − 压缩组累计输入 / 不压缩组累计输入 | 65 万 / 100 万，对应减少 35% |

表中是解释公式的假设数据，不是项目成绩。输出 token 单独统计，缓存字段单独报告。

单例通过要求 6 项都正确、未知项明确为 null、没有额外键、JSON 有效，并且循环正常结束。只找回 5 项有部分召回分，但用例不通过。超时或异常等未正常完成的运行，计入目标分母，按当前评分规则不给已知项召回分，同时保留原始答案检查结果。

**代码依据：** [recall_cases.py](D:/HarnessAgent/evals/recall_cases.py)、[recall50.py](D:/HarnessAgent/evals/recall50.py)、[token_usage.py](D:/HarnessAgent/evals/token_usage.py)。

### 20. 如何设计公平的上下文压缩对照实验？

**参考回答：** 同一个用例运行两次：一组关闭压缩，一组开启压缩。保持模型、初始历史、问题、工具定义、轮数与输出预算一致；使用独立工作区避免一组的文件影响另一组；交替两组执行顺序，减少固定顺序的影响。

**项目对应：** 当前记录并检查历史、问题和工具定义的哈希，设置子进程超时，分别保存结果。50 个用例各跑两组，共 100 次 Agent 运行，一次运行可能包含多次模型调用。

**边界：** 同样输入不保证 API 每次返回相同结果。当前默认每个条件运行一次，若要判断稳定性，需要重复实验；`--repeats` 重跑的是同样的条件，不会增加独立场景数量。

**代码依据：** [recall50.py](D:/HarnessAgent/evals/recall50.py)。

### 21. 项目已经统计 token，为什么压缩阈值还是字符数？

**参考回答：** 这是两个问题。触发压缩时，需要在发送请求前判断上下文大小，当前使用序列化消息字符量与消息条数作为近似；统计实际消耗时，读取供应商响应里的 `usage`。

**项目对应：** `LLMResponse` 保留原始 usage，评测包装器按可见调用记录，区分执行调用与摘要调用，再累计输入、输出和供应商提供的缓存字段。摘要调用的消耗也包括在对照统计里。

**边界：** 字符数不能直接当 token。某次缺失有效 usage 时，对应整批完整总量标为未知，不能补 0。缓存与推理细分字段不能未经确认就重复相加。SDK 内部重试请求不一定逐次暴露给包装器，因此这份统计不是保证完整的供应商账单明细。

**后续改进：** 增加兼容模型的请求前 token 估算，把压缩触发与真实窗口预算结合。当前仍需应急压缩作为兜底。

**代码依据：** [context.py](D:/HarnessAgent/agent/context.py)、[llm.py](D:/HarnessAgent/agent/llm.py)、[context_compaction.py](D:/HarnessAgent/evals/context_compaction.py)、[token_usage.py](D:/HarnessAgent/evals/token_usage.py)。

### 22. 50 个用例够不够？如果真实模型也全部答对，说明什么？

**参考回答：** 数量本身不能决定结论强弱，要看覆盖范围、题目独立性、难度和重复运行。全部答对只能说明模型在这批条件下通过，不能直接推成真实开发中召回率 100%。

**当前难度边界：** 普通工具历史的中等档有约 4.4 万噪声字符，高压档约 14.4 万；摘要类分别有 6 万和 12 万。但噪声主要是重复结构的日志，答案带明显 `PROJECT_NOTE` 标记，所以长度压力大，语义干扰有限。

**如何改进：** 引入自然语言需求、跨回合修订、相似值、真实工具错误，以及压缩后继续编码的任务；分类型看失败，而不是为了降低分数盲目增加噪声。还应区分用于调策略的用例和最终评估用例，避免只对这批模板优化。

**代码依据：** [recall_cases.py](D:/HarnessAgent/evals/recall_cases.py)。

## 六、失败分析与后续改进

### 23. 压缩后答错了，你怎么定位？

**参考回答：** 沿信息流查问题，而不是直接归因于模型差：

1. 初始历史有没有正确记录？标准答案规则是否明确？
2. 哪个压缩阶段处理了它？原文是否成功归档？
3. 摘要是否遗漏值、约束或版本？存档地址是否仍可访问？
4. 模型有没有读取存档？读取的内容是否包含目标？
5. 看到了正确记录后，是否仍选错版本、项目或 JSON 类型？
6. 是否因超时、轮数耗尽或输出截断未正常完成？

**项目对应：** 查看单次结果、答案、压缩记录、归档和 telemetry。批量运行保存检查点与报告，续跑会检查配置与代码签名，防止混用不同设置下的数据。存在日志不等于已经实现确定性的完整轨迹回放。

**可能追问：** 模型说任务完成了，但验收失败怎么办？以独立评分器和测试结果为准。编码任务应检查最终代码、测试与约束，而不是只判断回复里有没有“完成”。

**代码依据：** [recall50.py](D:/HarnessAgent/evals/recall50.py)、[context.py](D:/HarnessAgent/agent/context.py)、[verification_feedback.py](D:/HarnessAgent/evals/verification_feedback.py)。

### 24. 如果继续优化，你最先做什么？怎么证明改进有效？

**参考回答：** 我会先增加压缩后继续工作的真实任务。比如用户早期要求“修复登录，保持旧接口，不新增依赖”，中间经过大量文件读取与修改，然后压缩并继续完成任务。最终通过代码测试和约束检查验收，再对比全程 token 与耗时。

下一步根据失败类型改策略：摘要遗漏约束，就改摘要结构；查档困难，就改原文检索入口；触发太晚，就改请求前预算估算。每次改变保留一个对照基线，查看质量、开销和失败变化。

**边界：** 这是后续计划，不是当前 50 个召回用例已经覆盖的能力。当前也不能声称做过模型微调、强化学习、分布式调度或大规模线上验证。
