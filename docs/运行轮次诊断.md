# 运行轮次诊断

## 启动方式

在 PowerShell 的项目目录中运行：

```powershell
.\.venv\Scripts\python.exe -m agent
```

CLI 默认关闭线程团队和长期记忆，适合查找信息、单点修改等任务。权限检查、上下文压缩、
基础工具及一次性子 Agent 仍可使用；提示词要求小任务直接完成，不为单次查找委托子 Agent。
需要独立交付的并行任务时可开启团队：

```powershell
# 团队和长期记忆都开启
.\.venv\Scripts\python.exe -m agent --full

# 分别开启
.\.venv\Scripts\python.exe -m agent --teams
.\.venv\Scripts\python.exe -m agent --memory

# 显式关闭优先于--full
.\.venv\Scripts\python.exe -m agent --full --no-memory

# 免费离线检查，不调用真实模型
.\.venv\Scripts\python.exe -m agent --mock --demo --workdir .scratch\offline-demo
```

`Runtime.create()` 的 Python API 默认仍启用团队和记忆，已有评测和集成调用不会因 CLI
默认改变而自动换模式。真实模型的团队、摘要和记忆调用仍可能消耗 API 额度。

## 保存什么

每个 Runtime 会话有独立运行编号，文件默认位于：

```text
.agent/runs/<UTC时间-随机编号>/
  events.jsonl
  summary.json
```

事件持续写入并关闭文件；每个执行循环结束及 Runtime 关闭时更新汇总。
`loop_id` 区分主 Agent、一次性子 Agent和队友的执行循环，`parent_loop_id` 标明嵌套子循环。
`owner` 和 `round` 标明调用者与该循环内的轮次。并发写入和计数由同一把锁保护，线程上下文
使用 ContextVar 区分。日志不加入模型对话，因此不会占用下一轮模型上下文。

记录以下元数据：

- 每轮开始、准备后的消息数量和序列化字符量。
- 模型调用开始、结束、调用类别、耗时、输出文本长度、供应商结束原因和可用的 token 用量。
- 工具调用开始、结束、工具名、参数指纹、结果指纹及长度、耗时、错误码、执行状态。
- 校验、权限与执行阶段的恢复记录，以及程序计划自动重试的次数。
- 不完整响应恢复、上下文超限恢复和循环停止原因。

不保存提示词正文、用户请求正文、工具参数与结果正文、模型回答、内部思考或原始异常消息。
指纹用于比较是否相同，不用于恢复原文。`--verbose` 终端输出仍可能包含参数和结果片段，
它与这套元数据日志不同。

日志写入失败会显示 `trace_error`，不把成功任务改判为失败。崩溃前已经写入的事件可用于
分析中断位置；文件写入错误或进程强制终止可能造成缺失，不能视为完整的执行重放。

## 如何看统计

交互模式输入 `:trace`，也可以查看 `summary.json`。普通终端在任务返回时显示会话累计计数
和日志路径；`--quiet` 保持只输出最终答案。`--no-trace` 关闭元数据日志。

| 指标 | 含义 |
|---|---|
| `loop_rounds` | 所有已记录循环的轮次总和，包括主 Agent、子 Agent和队友 |
| `model_calls` | 模型客户端 `create()` 的调用次数，包含失败或尚未返回的调用 |
| `model_calls_by_kind` | 区分 `agent`、`summary`、三类记忆调用及默认目标评估器调用 |
| `by_owner` | 分别统计主 Agent、子 Agent、各队友的轮次与调用数；循环外调用单列为 `outside_loop` |
| `tool_calls` | 发起的工具调用数，包括被校验或权限拦截的调用 |
| `execution_attempts` | 真正进入工具 dispatch 的尝试数，自动重试会增加它 |
| `auto_retry_events` | 恢复管理器决定安排自动重试的次数，之后仍可能被权限拦截 |
| `tool_errors_by_code` | 每个最终工具结果的错误分类 |
| `coordination_calls` | todo、任务板、计划审批、队友通信和 worktree 等协调调用数 |
| `same_arguments_repeats` | 同一循环、工作目录内，相同工具及参数再次出现 |
| `same_read_result_repeats` | 同一循环内只读工具的参数和成功结果相同，期间未记录到该工作目录的潜在修改调用 |
| `loop_stop_reasons` | 各循环是正常完成、轮数耗尽、报错还是中断 |

一次模型回复可包含多个独立工具调用，它们仍属于同一轮。工具内部自动重试不会增加模型轮数。
摘要、记忆和目标评估可能增加模型调用数，但不是主 Agent 的工具轮次。供应商 SDK 内部的
HTTP 重试不拆成这里的独立调用。自定义目标评估器自行访问外部服务时，需要自行接入记录。

token 只采用实际返回的合法非负整数；某字段有一次缺失，该字段总计就是 null，不能把缺失
当作零。输入、输出和缓存字段分开统计，不自动计算费用。Mock 的计数只能验证流程。

## 重复观察的边界

第一版只记录，不缓存结果、不禁止重复调用，也不自动停止任务。

如果文件内容变化导致读取结果变化，不计为相同结果；该工作目录中发生潜在修改调用后，
旧的读取观察也会失效。Bash 可以产生副作用，因此不作为只读工具判断重复结果。

这个指标不能证明整个工作区没有外部变化，也不能证明重复验证无用。读取窗口外的变化、
外部进程操作、刻意重复验收等，都需要结合任务理解；不要直接据此当成死循环。

## 本次效率调整

系统提示词要求把参数已知、互不依赖的工具调用放在同一回复中；有依赖关系的调用继续等待
上一批结果。已有 Agent 循环本来就支持多工具调用，本次没有另加批量工具。
